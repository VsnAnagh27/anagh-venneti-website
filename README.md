# Anagh Venneti — Academic Website (Phase 3)

A lightweight academic website built with HTML, CSS and vanilla JavaScript. The existing Phase 1/2 design and publication pipeline have been retained. Phase 3 adds a professional timeline, a general blog landing page and an optional visitor-named document access register.

## What changed in Phase 3

- Removed the Projects page and its navigation entries.
- Added `pages/timeline.html` with an editable academic/professional chronology.
- Reworked `pages/notes.html` into a general Blog landing page. It currently displays four writing areas as **Under development**.
- Added a Markdown post directory (`blog/posts/`), a small index builder (`scripts/build_blog.py`) and a GitHub Actions workflow (`.github/workflows/build-blog.yml`).
- Added CV and PhD thesis links in the site navigation and relevant homepage/contact areas.
- Added a voluntary visitor-name prompt before a CV or thesis link opens.
- Added a Cloudflare Pages Function and D1 schema to store document access records.
- Added this deployment and maintenance guide.

assets/thesis.pdf

Copy your final, public thesis PDF into `assets/` and name it exactly `thesis.pdf`. Until you do this, the thesis link will lead to a missing file. No thesis document has been fabricated or substituted.

## Local preview

From this directory (the directory containing `index.html`):

```bash
python3 -m http.server 8080
```

Open <http://localhost:8080>. The static pages and visual layout can be checked locally. The visitor register requires the Cloudflare Pages Function and D1 database described below; a basic Python static server cannot execute that API.

## Document access register — how it works

### Visitor experience

When a visitor clicks a CV or thesis link:

1. A small dialog asks for their name.
2. They can choose **Continue and record** or **Continue without recording**.
3. If they provide a name and the API is configured, the server stores the name, document type, server timestamp and page path.
4. The requested PDF opens in a new tab.

This is a voluntary, self-reported name. It does **not** verify a person's identity, and it cannot reliably identify visitors who choose the anonymous route. It records a document-link click, not proof that the PDF was read or downloaded. Do not use this as an attendance, identity-verification or security system.

### Stored fields

| Field | Meaning |
|---|---|
| `visitor_name` | Name typed by the visitor (maximum 100 characters) |
| `document` | `cv` or `thesis` |
| `accessed_at` | Timestamp generated by the server in ISO 8601 UTC |
| `page` | Page path from which the link was clicked |

The database does not store the visitor's email address or ask for their institutional affiliation. The implementation does not deliberately collect IP addresses or browser fingerprints. The hosting provider may independently process technical request logs under its own policies.

### Deploy the register on Cloudflare Pages + D1

The included API is designed for Cloudflare Pages Functions. GitHub Pages alone is static hosting and cannot run this function or write to a database.

1. Create a Cloudflare account and connect this Git repository as a **Pages** project. Set the production branch to `main` and the build output directory to `.` (there is no build command). If you intend to use Cloudflare as the only production host, disable the existing `.github/workflows/deploy.yml` GitHub Pages deployment workflow (or disable GitHub Pages in repository settings) to avoid maintaining two live deployments.
2. In Cloudflare dashboard, create a D1 database named `anagh-document-access`.
3. Open the D1 console and execute the SQL in `functions/schema.sql`.
4. Copy the D1 database ID into `wrangler.toml`, replacing `REPLACE_WITH_YOUR_D1_DATABASE_ID`.
5. In the Pages project, open **Settings → Bindings → Add → D1 database**. Set the variable name to `ACCESS_DB` and select the database you created. Save and redeploy.
6. (Recommended) Add an environment variable named `ALLOWED_ORIGIN` containing your exact public site origin, for example `https://www.example.com`. Do not include a trailing slash. If you use more than one origin, separate them with commas.
7. Redeploy the site. Test a CV click with a test name and verify a row appears in D1.

The function is at `functions/api/document-access.js`; its route is `/api/document-access`. The frontend currently posts to that same-origin route. If you use a different API host, set `window.DOCUMENT_ACCESS_API` before `js/doc-access.js` loads, and configure CORS on that API.

### Viewing the access log

In Cloudflare dashboard, open **Workers & Pages → D1 → anagh-document-access → Console**, then run:

```sql
SELECT visitor_name, document, accessed_at, page
FROM document_access
ORDER BY accessed_at DESC;
```

For only thesis views:

```sql
SELECT visitor_name, accessed_at, page
FROM document_access
WHERE document = 'thesis'
ORDER BY accessed_at DESC;
```

Export the results from the D1 console if you want a local CSV/spreadsheet. Do not expose a public webpage that lists these names. Treat the register as personal data: disclose its purpose to visitors, restrict database access, retain entries only as long as needed, and delete records when no longer required.

### If you do not want Cloudflare D1

You can still host the static website on GitHub Pages, Netlify or Vercel. The PDF links and pages work as static content, but the included D1-based register will not work unless you configure a compatible backend. With the current code, failed logging is reported and visitors can still continue without recording. For the simplest all-in-one setup for this particular feature, use Cloudflare Pages + D1.

## Maintaining the timeline

Open `pages/timeline.html` and edit the `.timeline-item` entries. Each entry has a date/year, a category label, a heading and a short description. Add new entries in reverse chronological order (newest first) if you prefer a current-first presentation, or retain the existing chronological order. Verify dates and wording before publishing.

The current timeline is an initial draft based on the details represented in the Phase 2 site and information supplied for this phase. It is not an automatically verified CV. Review every entry, especially the exact date ranges, before publication.

## Writing and publishing blog posts

Blog sections currently appear as under development. To prepare a post:

1. Create a Markdown file in `blog/posts/`, for example `bayesian-inference-notes.md`.
2. Add YAML-style front matter at the top:

```yaml
---
title: "A title for the post"
date: 2026-11-19
category: Research & Ideas
summary: "A short description shown in the blog listing."
draft: true
---

Write the post body here in Markdown.
```

3. Keep `draft: true` while drafting. Change it to `draft: false` when ready to publish.
4. Run the index builder:

```bash
python3 scripts/build_blog.py
```

5. Commit and push the Markdown file and generated `data/blog-index.json`.

The workflow `.github/workflows/build-blog.yml` also rebuilds the index when blog posts or the builder change. Once at least one post is published (`draft: false`), it appears under **Published writing** on the Blog page and opens as an individual article page. The four broad blog areas remain marked under development until you decide to populate them. The original research-note Markdown files and note scripts are retained as source material, but the old notes interface is no longer linked as the public Blog.

## Hosting options

| Host | Best use | Notes for this site |
|---|---|---|
| **Cloudflare Pages + D1** | Recommended | Hosts static assets and runs the included API function; D1 stores the document access register. Git integration supports edits through GitHub. |
| **GitHub Pages** | Simplest static hosting | Excellent if you only need the website and PDFs. The D1 access register function will not execute on GitHub Pages. Supports custom domains. |
| **Netlify** | Managed static hosting | Git-based deployment and serverless functions are available; you would need to adapt the included Cloudflare function/database integration. |
| **Vercel** | More application-oriented hosting | Git-based deployment and functions; useful if the site later moves to a framework, but unnecessary for the current static architecture. |

### Recommended workflow for future changes

1. Keep the website source in a GitHub repository.
2. Connect that repository to Cloudflare Pages.
3. Make edits locally in VS Code (or edit files directly on GitHub for small text changes).
4. Preview with `python3 -m http.server 8080`.
5. Commit and push to GitHub; Cloudflare Pages automatically deploys the update.
6. Keep a copy of the D1 database and periodically export the access register if you need an independent record.
